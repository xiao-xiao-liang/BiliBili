# M5：故障恢复、资源验证与作品交付

状态：待评审，未执行。前置为 M1～M4 功能可运行。M5 不新建业务表，也不把可靠性机制留到此时才设计；它集中证明前面约定的行为在故障下成立。

## 1. 本阶段边界

沿用全部业务接口和数据模型。新增的是可重复的故障测试、资源采集、启动/恢复手册与验收报告；不新增生产环境“任意重置状态/执行 SQL/伪造用户”的调试接口。故障钩子只存在于测试构建或隔离测试进程。

## 2. 故障矩阵与最终不变量

| 注入点 | 可见行为 | 必须成立的最终状态 |
| --- | --- | --- |
| API 在创建投稿提交后、返回前退出 | 前端可重试 | 同幂等键只有一个投稿 |
| multipart 初始化成功但回写失败 | 会话准备中，可恢复 | 一个有效会话，额外 multipart 被回收 |
| 浏览器分片中断或签名过期 | 缺片可续传 | 已确认片不重传，结果哈希一致 |
| Complete 成功但 API 未记录 | completing 可对账恢复 | 一个 completed 会话、一个校验工作意图 |
| 数据库提交任务后 MQ 不可用 | 处理中等待 | Outbox 保留；恢复后执行 |
| 发布确认丢失 | 可能重复投递 | 只接受一次有效业务结果 |
| broker 重投达到上限 | 明确失败或等待清理恢复 | 消息进入隔离队列；有效任务可对账，不静默消失 |
| worker 领取后退出 | 处理可恢复 | 租约过期，旧资格失效，新尝试接管 |
| FFmpeg 中途退出 | 显示重试或失败 | 当前档可重做，ready 档保留 |
| 对象已上传而任务事务回滚 | 暂不发布 | 孤立对象不被引用，后续可回收 |
| 数据库成功但消息 ack 丢失 | 消息重投 | 已完成任务不再次转码或发布 |
| 旧进程在新租约产生后回写 | 用户不被旧结果影响 | 旧 lease_token 的提交失败 |
| 发布与删除同时发生 | 删除后不可访问 | 最终 deleted，无法再次 published |
| 删除时 RustFS 不可用 | 内容立即不可见 | 清理任务保留，恢复后最终无残留 |
| Token 到期/当前端退出 | 当前端重新登录 | 不影响其他未过期端，不删除投稿 |

每项都记录初始数据、触发动作、故障位置、恢复动作、HTTP 最终结果、数据库关键状态和对象最终清单。只有日志打印“重试成功”不能作为不变量成立的证据。

## 3. 孤立资源与维护约定

维护扫描默认每五分钟执行小批次。对象属于有效 running 租约时不能清理；普通 staging 孤立对象至少超过两小时宽限，且没有有效投稿/任务引用才可回收。删除投稿使用 M4 更短的静默观察和复查规则。

处理过程中创建的临时目录带任务/租约标识。恢复时对照数据库：有效执行目录保留，失效目录在工作进程确认不再使用后清理。源文件仍在 RustFS，临时目录丢失不能导致必须让作者重新上传。

幂等记录超过七天可回收；删除投稿的墓碑及与在途消息相关的任务标识不能立即物理删除。第一版暂不自动压缩任务审计历史，避免未经验证的历史清理破坏去重。

## 4. 并发和资源场景

在同一台机器上同时运行：一个接近上限但合法的上传、一个目标档位转码、两个独立 Chrome 会话观看已发布视频。观察播放是否能继续、JSON 请求是否响应、上传是否推进；不用“每秒多少请求”代替实际用户流程。

记录：源视频时长/尺寸、每档处理耗时、CPU、进程/容器内存、对象与临时目录磁盘占用、队列积压、任务重试、HTTP 错误/耗时。容器上限、RabbitMQ 水位和实际内存分别记录。先测量后调整并发/线程/限额，任何调整更新规格参数及报告。

## 5. 运行与恢复文档必须回答的问题

- 如何在保留持久数据的前提下启动、停止和重启各进程？
- 首次迁移、后续迁移和数据库版本检查如何执行？源/目标版本是什么？
- 处理卡住时如何由投稿 ID 找到任务、尝试、Outbox 与请求日志？
- RabbitMQ、Redis 或 RustFS 停止时哪些能力暂时受影响，如何确认恢复？
- 怎样检查孤立文件，如何确保不会误删有效成果？
- 如何备份并恢复 PostgreSQL 与媒体目录的一致副本？第一版采用停止写入及后台任务后的联合备份，不把 pg_dump 当作媒体备份；Redis 登录态能恢复则恢复，否则明确让用户重新登录。
- 哪些操作会销毁本地数据？普通启动手册不能默认执行它们。
